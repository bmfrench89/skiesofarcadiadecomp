**Why.** Everything a mod author needs exists, scattered: the grammar in README's `SOA_MODS` row and
`runtime/mod.c`'s header, the API in `runtime/soa_mod.h`, the rules in plans, the build line in
`examples/mods/map-log/mod.c`, and the only way to try a mod without the game is a test file's private driver.
T10 puts them in one guide and one tool.

## 1. `tools/mod.py`

```
python tools/mod.py new DIR [--dll]       # a mod folder at DIR, ready to edit
python tools/mod.py build DIR             # mod.c -> mod.dll (mod.so off Windows), for this machine
python tools/mod.py check DIR [--dol F]   # load it against your DOL, no game started
python tools/mod.py test DIR [SCRIPT]     # run it on the fake guest, no disc needed
python tools/mod.py api                   # print docs/MODDING-API.md from runtime/soa_mod.h
```

- **new** writes `mod.ini` (manifest 2, the id DIR's folder name, version 1.0, `api = 1`, the `dol_sha1`
  `config/GEAE8P/config.yml` pins) and a `patches.txt` of comments; `--dll` adds a `mod.c` from
  `examples/mods/map-log`'s pattern instead. The folder's name must be an id (lowercase letters, digits, '.',
  '_' and '-'); an existing folder is never overwritten.
- **build** compiles `mod.c` beside its `mod.ini` with the toolchain the port uses (MSVC through
  `toolchain.cc`, which finds the compiler itself: no developer prompt), then reads the library's header and
  refuses one built for a machine other than the port's (x86-64 here; arm64 on an arm64 host, so nothing
  assumes x86), naming what it is. A 32-bit `mod.dll` today fails inside the port as
  a bare "error 193".
- **check** builds the fake-guest driver and runs `mod_load` from the port's own `runtime/mod.c` over the mod
  against the real DOL (`extracted/sys/main.dol` unless `--dol`), printing what the port would: the load or
  the refusal with its file and line, each write listed (M17), the options (M16). `SOA_MOD_OPT` is passed
  through. A library beside it is checked against the port's machine before it is loaded. Exit 0 when it loads.
- **test** runs the mod on the fake guest with its `dol_sha1` swapped for the fake DOL's (the fake DOL has one
  code section and nothing of the game), then a script of the driver's commands (`set`, `frame`, `safe`,
  `get`, ...; listed by `--help`), and prints what came out. It checks that a mod loads, its grammar, its
  callbacks and the API's refusals -- not what it does in the game: there are no game functions for
  `call_guest` but the stand-in at `0x80003100`. The guide says so.
- **The driver moves** from `tools/tests/test_mods.py` into `tools/soa/modkit.py`, which `test_mods.py`
  imports, so the tests and the tool cannot drift.

## 2. `docs/MODDING.md`

A first patch mod in fifteen minutes (`new`, a `patches.txt` line, `check`, a run); finding an address (peeks,
the research docs, the map and flag words this project already names); the `patches.txt` grammar whole; options
(M16) and order and conflicts (M17); a native mod (`new --dll`, `build`, the callbacks and where each runs);
the rules the plans promise but never place:

- `on_frame_end` runs inside the XFB copy: memory writes only, never `call_guest`;
- `call_guest` only from a safe point, scene or map callback;
- every callback runs on the guest CPU thread: never call the API from a thread of your own;
- registration closes when `soa_mod_init` returns;
- check `api->size` against `SOA_MOD_HAS(member)` for anything appended;
- pointer patches belong on load triggers: in a battle `0x803474BC` still names the field's table while its
  memory holds something else (FINDINGS "R5c and M6 on the PC");
- a recording replays with the same mods; pad 2 and host buttons are not recorded yet;
- no game data in a mod: `tools/guard.py` refuses anything in a mod folder that is not text.

## 3. The API reference

`docs/MODDING-API.md` is generated by `mod.py api` from `soa_mod.h`: each `SoaModApi` member in order with the
comment above it, the button and host constants, and the structs. A test regenerates it and compares, so it
cannot go stale.
