# Make 60 fps the default, after four fixes

Every port that took a 30 fps console game to 60 fps without breaking it, on an engine with no delta time (no variable saying how much time has passed), did what this port does. It kept the game's logic at 30 updates a second and drew in-between images. Letting the logic run faster worked only where the engine already measured elapsed time, as in Sonic Unleashed, Perfect Dark and Super Mario Sunshine. Two teams that tried it on fixed-step games, Dinosaur Planet Recompiled and BlueWake (Wind Waker), took the option back out. A second recompilation of this very game, ogdanimal's GPL-3.0 "Skies of Arcadia Legends: Recompiled", ships interpolated 60 fps and writes down the traps it hit in Skies. The mature answer for arbitrary screens is RT64's "Display" mode: it interpolates to whatever rate the screen refreshes at, spaces the in-between images evenly in time, and skips them when the machine falls behind. This port's fixed one-in-between design is smooth only at 60 or 120 Hz, so the owner's 85 Hz monitor and a Steam Deck OLED at 90 Hz get no in-between images at all. Shipped defaults follow how far each team trusts its interpolator, not the device. The N64 recompilations, which hand-tag hundreds of objects, ship "match the display"; Ship of Harkinian, Dusklight, BlueWake, Dinosaur Planet and Ghostship's Android build store the original rate as their default. **My recommendation: yes, smooth motion should become the default, but not yet, and only on the GPU renderer.** It leaves the game's speed and rules alone and costs one 60 Hz refresh (16.7 ms) of delay. Before it becomes the default, it needs the owner's in-person look (session D), a display-rate mode, a visible fallback, and fixes for whatever that look finds. The CPU renderer should stay at 30 because it reaches only 32–43 images a second. Android should stay at 30 until the GPU backend is shown running on a phone.

## Ports with no delta time reached 60 only by leaving the logic at 30

Skies cannot simply be unlocked. The project's own code study found that the cap is an immediate value of 1 at 0x801DC4A4 in the frame-end function, and that every system steps once per frame with no clock to scale (`docs/research/frame-pacing.md`). The community found the same on the Dreamcast: when someone asked for a 60 fps code, the reply was "Yes Arcadia is double speed everywhere" ([ASSEMBLERgames](https://assemblergames.org/viewtopic.php?t=9915&start=40)). A 2007 Dreamcast emulator that ran it at 60 drew the complaint "60 fps is waaay too fast" ([EmuTalk](https://www.emutalk.net/threads/can-i-play-skies-of-arcadia-at-30-fps-instead-of-60-fps-60-is-too-fast.41620/)). Dolphin ships no 60 fps code for the game; its settings file for Skies only forces single-core mode and two texture settings ([Dolphin GEA.ini](https://raw.githubusercontent.com/dolphin-emu/dolphin/master/Data/Sys/GameSettings/GEA.ini)). Across the whole GameCube library, Dolphin ships named 60 fps codes for **just 13 games**, against 150 settings files with a widescreen code ([Dolphin GameSettings](https://github.com/dolphin-emu/dolphin/tree/master/Data/Sys/GameSettings)). Those codes cluster where the game already had a frame-rate setting, such as Pikmin 2's `setFramerate`, and even then their notes admit sped-up particles, UI and camera. A fan hack that tried to double Wind Waker's logic produced scripts that "run twice as often", enemies that attack twice as often and timers that softlock Ganon's Castle ([Wind-Waker-60FPS-Hack](https://github.com/Meowmaritus/Wind-Waker-60FPS-Hack)).

The ports that did unlock logic all started from engines that already measured time. Sonic Unleashed "simply follows the time step as closely as possible" ([UnleashedRecomp](https://github.com/hedge-dev/UnleashedRecomp)). The Sunshine port doubles what the game's own `SMSGetVSyncTimesPerSec` returns, then fixes the leftover frame counters one at a time across **45 separate patches** ([sms-pc-port](https://github.com/chasem-dev/sms-pc-port/tree/HEAD/decomp-patches)). Perfect Dark's engine already counted 60 Hz and 240 Hz ticks ([perfect_dark timing.c](https://github.com/fgsfdsfgs/perfect_dark/blob/port/src/game/timing.c)). Where the engine counted frames, attempts were withdrawn. Dinosaur Planet added a "60 Hz Gameplay" option, then switched users off it because it "really isn't safe at the time of writing and we should encourage users to migrate to frame interpolation instead", and removed it nine days later ([dino-recomp b2c2e41a](https://github.com/DinosaurPlanetRecomp/dino-recomp/commit/b2c2e41a), [cfa8e2f3](https://github.com/DinosaurPlanetRecomp/dino-recomp/commit/cfa8e2f3)). BlueWake's README now says "0.4.0's experimental 60 FPS game logic is gone" ([BlueWake](https://github.com/chrissotraidis/bluewake)). Sega's own Shenmue I & II remaster stayed locked at 30 because "the game code of the original series is coded to assume that the game's target framerate is 30FPS" ([Overclock3D](https://overclock3d.net/news/software/shenmue-i-ii-will-be-locked-to-30fps-on-all-platforms/)).

Among the interpolating ports, the main difference is how they work out which object in one frame is which object in the next. RT64, the renderer behind the N64 recompilations, matches objects by ID numbers that hand-written patches attach to the game's matrices: about 125 tag sites in Majora's Mask ([Zelda64Recomp patches](https://github.com/Zelda64Recomp/Zelda64Recomp/tree/dev/patches)) and about 389 in Star Fox 64 ([Starfox64Recomp](https://github.com/sonicdcer/Starfox64Recomp)). Anything left untagged falls back to an automatic matcher that RT64's README calls "a highly experimental area that is prone to errors" ([RT64](https://github.com/rt64/rt64)). Its author says that matcher skips "very large movements" ([Zelda64Recomp #654](https://github.com/Zelda64Recomp/Zelda64Recomp/issues/654)). Ship of Harkinian labels objects by hand in **143 places across 59 files** ([SoH z_actor.c](https://github.com/HarbourMasters/Shipwright/blob/develop/soh/src/code/z_actor.c)). Dusklight's interpolation touches 70 files ([code search](https://github.com/search?q=repo%3ATwilitRealm%2Fdusklight+%22dusk%3A%3Ainterp%22&type=code)), and its author called the work "a nightmare at times" ([PR #2431](https://github.com/TwilitRealm/dusklight/pull/2431)). The closest relatives to this port match draw calls with no tags. BlueWake captures each draw, matches it on a helper thread and blends cloth, water and particles vertex by vertex ([patch 0132](https://github.com/chrissotraidis/bluewake/blob/HEAD/patches/recompcore/0132-display-rate-and-slow-game-interpolation.patch)). ICO-pc does the same in a 6,158-line replay interpolator ([rd_interp.c](https://github.com/nathanialf/ico-pc/blob/HEAD/port/render/rd_interp.c)). This port matches automatically too, which is RT64's fallback path, because only 83 of 7,144 functions are decompiled and so there is little game code to put tags in. ICO-pc also flags a limit that applies here. It rotates matrices properly rather than blending them number by number, because blended numbers mean "a turn of 77 degrees in a tick ... would draw a bone 22 % short half way" (same source). This port blends vertex positions in straight lines, so **an object that turns fast within one frame will shrink at the midpoint**. That is my inference from ICO-pc's figure; nobody has looked at it in this port.

## A second Skies recompilation already ships 60, and its notes map this game's traps

"Skies of Arcadia Legends: Recompiled" by ogdanimal is a static recompilation of the same disc for Windows, Linux and Android. It was started in October 2026, takes its graphics, sound and input from Dolphin's hardware code, and is licensed GPL-3.0. The tracker counted 213 commits in its first 30 days ([recompsoftware.com](https://recompsoftware.com/p/skies-of-arcadia-legends-recomp/)). Its README promises "**60 fps** by frame interpolation, or the original 30". It says a Retroid Pocket 5 (Snapdragon 865) "runs it at full speed at 60 fps". On slower devices the settings menu opens once on Frame rate, and nothing changes automatically ([README](https://github.com/ogdanimal/SkiesOfArcadiaLegends-Recomp)). That behaviour implies 60 is on by default, but the notes do not quote its stored default.

Its design is this port's design reached independently. "The game logic is fixed-step at 30 Hz", so it records each frame's GX command stream (the stream of drawing commands the game sends to the graphics chip) and replays it with positions halfway between the previous frame and the current one ([development notes](https://raw.githubusercontent.com/ogdanimal/SkiesOfArcadiaLegends-Recomp/main/docs/development-notes.md)). Its measurements say something specific about Skies. The game's Ninja engine transforms vertices on the CPU, so the graphics chip's matrices "barely change" (about 2 of 2,400 matrix loads per cutscene frame), while **about 4,200 draws and 24,000 vertices per frame carry the motion**. From that measurement I infer that matrix-based interpolation, the method RT64, Ship of Harkinian and Dusklight use, would see almost nothing move in Skies. Matching draws and blending vertices, which is what this port already does, is the method that fits this game. ogdanimal pairs draws "by vertex format, count and texture" and aligns lists by the position of their first vertex. It shows the in-between image on the first retrace and the real frame on the second, and measured "59.9 presented fps at speed 1.0" with 299 of 300 frames interpolated. It rejected a game-side 60 fps patch because that needs "~2.0× headroom in every scene" against the 1.02–1.05× it had on Android. Its end-of-frame retrace waits at 0x801DC498 and 0x801DC4D8 sit either side of this port's cap at 0x801DC4A4 in the same function, which independently confirms where the cap lives. That last point is an inference, but a strong one.

Its list of failures and fixes doubles as a checklist for this port, as do the problems it still had open. Title-screen clouds flickered when the n-th draw was paired with the n-th draw. Stray bands appeared while steering the ship because culling one object shifted every later pairing; its fix took the steering test from 17 of 417 bad images to 0. Sky-blue cracks opened along cliff edges. Battle transitions broke. A full-screen quad jumping in depth produced black in-between images, a replay that reloaded texture memory put garbage on the cloud sea, and copies of the picture that the replay encoded differently put green bands on the Retroid. Jumps of 370 units count as teleports. On 2026-10-07 it still listed **"scene cuts and particles, where unpaired draws show the new frame"** and **"EFB copies that the next frame reads (the afterimage effect)"** as open (same source). Those are three of this port's five planned artifact classes (particles, missed camera cuts and texture copies). Some of its problems probably will not carry over. This port's in-between pass skips copies to texture and never writes the game's memory (`docs/research/frame-pacing.md`), so the texture-memory corruption should not happen here in the same form; that is an inference, not yet checked. It also turns interpolation off during sped-up battles except for spells. This port already does the equivalent: it stops building in-between images while turbo is on (`runtime/window.c`).

The licence matters. The other project is GPL-3.0 and built on Dolphin's GPL code, while this project is MIT-licensed (`LICENSE`). Reading its notes and learning from its ideas is fine. Copying its code or patches, or closely translating them, would put the combined work under the GPL, and **that needs a deliberate licence decision from the owner before any of it enters this repository**. Its development notes are long (about 281,000 characters), and the researcher read them only through a summariser, so some sections were never fully seen. Because it needs the same disc, it also gives the owner a reference to play the same scenes in, side by side.

## Serving every screen means interpolating to its refresh rate, not doubling

A screen's refresh rate is how many times a second it redraws. When a game's image rate does not divide into it evenly, some images stay on screen longer than others, and the uneven motion is called judder. At 144 Hz, a fixed 60 images a second stay up for 2, 2, 3, 2, 3 refreshes; at 90 Hz the pattern is 2, 1, 2, 1 (devices and pacing notes, worked from the arithmetic). Today the port shows in-between images only when the refresh rate is within 2% of 60, 120, 180 or 240 Hz (`runtime/picture.c`, `present_interp`). At 120 Hz it builds the same single in-between and holds every image for two refreshes, so the Ally X's screen gets 60 distinct images a second, not 120. A variable-refresh (VRR) screen, one that waits for the game's next image instead of redrawing on a fixed clock, is not used for pacing either. The Vulkan presenter requests the FIFO present mode only (`runtime/gxv.c`), and no tearing flag appears in the runtime. Microsoft says "Variable refresh rate displays require tearing to be enabled", and the tearing flag works only with sync interval 0 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/variable-refresh-rate-displays)).

| Device and screen | What the port shows today (`interp = 1`, `gpu = vulkan`) | What a display-rate mode would show |
|---|---|---|
| ROG Ally X screen, 120 Hz, FreeSync Premium | 60 distinct images a second, each held for two refreshes | up to 120 (three in-betweens per real frame) |
| Owner's docked monitor, 85 Hz | no in-between images: 30 real frames, unevenly held | 85 (about 2.8 images per real frame) |
| Steam Deck LCD, 60 Hz (40–60 Hz slider) | 60 at 60 Hz; none at 40 Hz | 60, or 40 at the 40 Hz setting |
| Steam Deck OLED, up to 90 Hz | none at 90 Hz; 60 only if the player sets 60 Hz | 90 (three images per real frame) |
| Android flagship, refresh chosen by the system | whatever rate Android picks; the port requests none | 60 by request, as Google advises for games |

RT64 solves this most completely. It has three modes, Original, Display and Manual. Display targets the rate the swap chain (the queue of finished images waiting for the screen) reports, Manual is limited to that rate, and Original turns interpolation off ([rt64_workload_queue.cpp](https://github.com/rt64/rt64/blob/main/src/hle/rt64_workload_queue.cpp)). An integer counter decides how many images each game frame gets and gives every image its own blend weight, **evenly spaced in time rather than fixed at the halfway point**. At 144 Hz over 30 fps logic that comes to 4.8 images per game frame: four game frames get five images and the fifth gets four. RT64 measures the refresh rate again whenever the window is resized or moved, so dragging the window to another monitor retargets it ([rt64_present_queue.cpp](https://github.com/rt64/rt64/blob/main/src/hle/rt64_present_queue.cpp)). It rounds rates ending in 9 up, so 59 counts as 60 ([rt64_application_window.cpp](https://github.com/rt64/rt64/blob/main/src/hle/rt64_application_window.cpp)). When it falls behind, it renders one in-between image fewer. BlueWake goes up to 7 in-betweens for a 240 Hz screen ([patch 0132](https://github.com/chrissotraidis/bluewake/blob/HEAD/patches/recompcore/0132-display-rate-and-slow-game-interpolation.patch)). ICO-pc measures how fast the screen really refreshes "rather than the number Windows reports" and treats 143 Hz as 144 ([ICO-pc options](https://github.com/nathanialf/ico-pc/blob/HEAD/docs/OPTIONS.md)). This port is closer to that than it looks. Its blend already takes the weight as a parameter (`gxr_pair_mode(..., 0.5f)` in `runtime/gxr.c`), but the live path builds exactly one image per real frame, so a display-rate mode means building several images with different weights and pacing them. Measured at about 1.35 ms of GPU time per in-between, three in-betweens per real frame at 120 Hz come to roughly 4 ms in a 33 ms frame. That figure assumes the cost scales linearly and has not been measured.

The pacing practice the projects agree on is a flip-model swap chain (Windows' efficient way to hand images to the screen) with a waitable object and at most 1–2 frames queued. On a fixed-refresh screen that means vsync; on a VRR screen it means sync interval 0 with tearing allowed and the game's own limiter keeping the rate inside the screen's range ([Microsoft Learn: flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)). Alen Ladavac's GDC 2018 talk explains why timing frames by how long they took to render causes micro-stutter, and why pacing should follow when each image actually reaches the screen ([GDC Vault](https://gdcvault.com/browse/gdc-18/play/1025031), [Phoronix](https://www.phoronix.com/news/Frame-Timing-Game-Stuttering)). Zelda64Recomp and Unleashed both warn that external frame limiters cause stutter ([Zelda64Recomp](https://github.com/Zelda64Recomp/Zelda64Recomp)).

The Steam Deck and Android each add their own wrinkle. Valve's only performance bar is "30fps at 800p" with the default settings, and it explicitly allows per-device defaults ([Steamworks compatibility](https://partner.steamgames.com/doc/steamdeck/compat), [recommendations](https://partner.steamgames.com/doc/steamdeck/recommendations)). The OLED model runs "up to 90Hz" ([steamdeck.com](https://www.steamdeck.com/en/tech)), and since November 2023 a single frame-limit slider also picks the refresh rate ([GamingOnLinux](http://www.gamingonlinux.com/2023/11/valve-refines-new-steam-deck-unified-frame-limit-slider-to-show-refresh-rate)). Players report Proton games seeing 90 Hz whatever the slider says, which is anecdotal ([Steam Community](https://steamcommunity.com/app/3180240/discussions/0/4625855365895977959)), so whether this port detects the right rate under Proton needs a real Deck to answer. On Android the system decides the refresh rate. Android 15 sets games to 60 Hz by default ([Android: refresh rates](https://developer.android.com/games/optimize/display-refresh-rate-change)). Google's own example is a game calling `setFrameRate(60, FRAME_RATE_COMPATIBILITY_DEFAULT)` once, so that a 90 Hz phone drops to 60 rather than judder ([Android: frame rate](https://developer.android.com/media/optimize/performance/frame-rate)). PPSSPP ships exactly that as its default ([PPSSPP Config.cpp](https://github.com/hrydgard/ppsspp/blob/master/Core/Config.cpp)). Google also says to lower peak frame rates in Battery game mode ([Game Mode API](https://developer.android.com/games/gamemode/gamemode-api)) and to read thermal headroom no more than once every 10 seconds ([Thermal API](https://developer.android.com/games/optimize/adpf/thermal)). This port's runtime makes no `setFrameRate` call today. Its Android spec plans `setFrameRate(window, 30, ...)` on every new surface, and 60 only under turbo, a step that waits for a real phone (`docs/specs/android.md` §3.12). With interpolation on, that request has to be 60, or Android will hold the screen at a rate with no room for in-between images. The GPU backend has no Android-specific code (no `__ANDROID__` in `runtime/gxv.c`), and the notes do not establish that it runs on a phone at all.

External frame generation does not replace any of this. AMD's AFMF 2 runs on the Ally X, but AMD wants a base of at least 45–50 fps ([HotHardware](https://hothardware.com/news/amd-fmf2-on-rog-ally-x)). Lossless Scaling treats 30 fps as its floor at 1080p ([LSFG 3](https://losslessscaling.com/lsfg-3/)). These tools see only finished pixels, so they smear HUD text, and they judder when a 30 fps game sends each image twice ([Steam thread](https://steamcommunity.com/app/993090/discussions/0/4429939323287226285/)). On the Deck they exist only as the third-party lsfg-vk ([decky-lsfg-vk](https://github.com/xXJSONDeruloXx/decky-lsfg-vk)). I infer that the built-in interpolator is the only route that reaches every target device on equal terms.

The pattern is confidence. Teams whose games are tagged almost everywhere ship "on". Teams with gaps ship "off", or retreat to it, as Dinosaur Planet did when its framebuffer effects were only partly supported. Dusklight's path is the most useful one to copy. It kept the stored default off but put interpolation into the "Our recommended way to play!" preset that every new player is asked to choose. Its help text softened from "Experimental feature: Visual artifacts, animation glitches, or instability may occur" to "minor visual artifacts" as the work matured ([commit 55455bb](https://github.com/TwilitRealm/dusklight/commit/55455bb1b5)). Almost nobody changes the default by device. Zelda64Recomp's Steam Deck detection only chooses fullscreen. ICO-pc starts phones at 60. Ghostship's Android build keeps 30. Lost Odyssey caps fast loading on battery devices. No project was found that detects a weak device and lowers its frame rate by itself.

The safety net is automatic. RT64 drops in-between images that would miss their slot. BlueWake measured its game slowing to 24–28 game frames a second on four small cores. It now treats game frames averaging more than 35.5 ms apart as an overload, drops the in-betweens, and doubles the waiting time before it tries again, up to 2 minutes ([patch 0132](https://github.com/chrissotraidis/bluewake/blob/HEAD/patches/recompcore/0132-display-rate-and-slow-game-interpolation.patch)). It also fixed an FPS overlay that read 60 while the picture moved at 30 ([patch 0151](https://github.com/chrissotraidis/bluewake/blob/HEAD/patches/recompcore/0151-fps-overlay-says-when-smooth-motion-is-paused.patch)). This port's budget, which stops after three frames over 35 ms and backs off before restarting, is the same idea, already built. What it lacks is telling the player, as BlueWake's counter and ogdanimal's one-time menu do.

Interpolation costs delay, but little, and nobody has measured it. Ship of Harkinian calls interpolation "purely visual", and Zelda64Recomp says "changing framerate has no effect on gameplay" ([Zelda64Recomp](https://github.com/Zelda64Recomp/Zelda64Recomp)). Because every in-between image blends from the previous frame towards the current one, the newest game state reaches the screen fully one 60 Hz refresh later at 30-to-60. This port's own log says so: "every real frame a 60 Hz refresh later than without" (`runtime/window.c`). Movement towards the new state still begins on the very next refresh. Working from RT64's weights, a display-rate mode raises that delay to (N−1)/N of a game frame, where N is the number of images per game frame: about 25 ms at 120 Hz. That is my calculation, not anyone's measurement, and no project has published a measured input-lag figure for interpolation on versus off. For a turn-based JRPG it is a small price, and an "Original (30)" switch removes it. Demand cuts the other way. Skies players have asked for speed rather than smoothness: a Dolphin tester "completed the full story at 200% speed" ([Dolphin wiki](https://wiki.dolphin-emu.org/index.php?title=Skies_of_Arcadia_Legends)), and ogdanimal headlines 2x to 4x battle speed. A 60 fps default will be judged next to turbo. The research found no players asking for 60, though its Reddit searches came back empty, so that proves little.

## What has to happen before 60 becomes the default

The end state I recommend is a frame-rate setting with RT64's three choices: **Original (30)**, **Display** (one in-between image per refresh, whatever the screen's rate) and **Manual** (a cap such as 60, never above the screen's rate). Display should be the default wherever the GPU backend runs, on Windows PCs, handhelds and the Steam Deck. The CPU renderer should always run at Original and say why, because it cannot hold 60. On Android the port should request 60 Hz once at startup, interpolate to 60 only when the GPU backend runs and keeps up, and drop to 30 in Battery game mode or when thermal headroom runs short. One open question belongs to the owner, because no source measured it: on the Ally X, does Display at 120 Hz cost enough battery compared with Manual 60 to make Manual 60 the better handheld default? Measuring the wattage of both modes on that machine answers it. The way there has stages. Today interpolation stays off. Once session D finds nothing blocking on the GPU renderer at 60 or 120 Hz, offer it as the recommended choice on a first-run screen, as Dusklight does, with the stored default still 30. Make it the outright default once the four items below are done.

The first item is the renderer. The GPU backend must become the default, or the interpolation default must be tied to it, because the CPU path reaches only 32–43 images a second. The second is any-refresh support: build the Display and Manual modes with evenly spaced weights using RT64's counter, measure the refresh again when the window moves to another monitor, round 59.94 to 60, and on Android request 60 rather than the spec's planned 30 whenever interpolation is on. Using VRR, with tearing allowed inside the screen's range, is optional extra work. On the Ally X's 120 Hz screen the current FIFO path is designed to hold every image for an even two refreshes, though nobody will know whether it does until session D. The third is a fallback the player can see. Keep the 35 ms budget, skip individual in-betweens when several are due per real frame (RT64's frame reduction), show the true image rate when interpolation pauses, and tell the player once if the device cannot hold the rate. The fourth is the artifacts: fix every class session D finds, or snap that class to repeating the real frame, which is H18's own rule. ogdanimal's open list says to expect particles, missed cuts and the afterimage copy, and other projects show cheap snap points. ICO-pc snaps "at a fade edge" ([rd_interp.c](https://github.com/nathanialf/ico-pc/blob/HEAD/port/render/rd_interp.c)), and Dusklight calls a presentation sync from its event camera ([code search](https://github.com/search?q=repo%3ATwilitRealm%2Fdusklight+request_presentation_sync&type=code)). Because this port already hooks game functions through `hooks.txt`, it can catch the game's fade task (fn_801CBA98) and its event-camera cuts without decompiling them. That is an inference worth testing, not a measured fix.

## Conclusion

The question is less "60 or 30" than who absorbs the matcher's mistakes. This port matches automatically, which is the path RT64's own author calls experimental, and with so little decompiled code it cannot lean on tags the way the N64 ports do. What makes a default defensible anyway is the design already built: when matching fails, the port repeats the real frame. A wrong match costs one smeared 16 ms image, and a skipped one costs a moment at 30. So the work before flipping the default goes mostly into making the snaps catch every bad case (cuts, fades, particles, copies), not into making every match perfect, and the owner's session D list is what tells that work where to aim.

ogdanimal's project changes the stakes more than the plan. Players will soon be able to compare two 60 fps versions of Skies, and that project's unsolved problems are exactly the ones this port has not yet looked at, so neither has a lead on the hard part. The display-rate mode is the one change that turns "smooth on 60 and 120 Hz screens" into "smooth on every target screen", including the 85 Hz monitor on the owner's own desk.
